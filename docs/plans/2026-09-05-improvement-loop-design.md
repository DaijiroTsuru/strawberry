作成日: 2026-09-05

## 1. 目的

津留いちご園ECサイトについて、「計測 → 仮説 → 施策 → 検証」を週次で自動的に回し、
年々売上を改善していくループを構築する。AIが自動で実行できる範囲を最大化し、
運用コストは可能な限りゼロに近づける。

## 3. 却下した前提

設計初期に立てた前提のうち、実データによって否定されたもの。同じ誤りを繰り返さないため記録する。

| 却下した前提 | 却下理由 |
|---|---|
| 前年同期比（YoY）で季節変動を吸収する | GA4データが2025-12開始のため、**2026-12まで実行不可能** |
| サイト全体のCVRを主指標にする | EC購入といちご狩り予約という別事業が同一分母に混在している |
| A/Bテストで施策を検証する | CVR 0.87%→1.3%（相対+50%）の検出に1群約1万セッション必要。ピーク期でも1群3ヶ月かかり成立しない |
| 季節性が最大の課題である | 売上は季節でほぼ動かない。課題は流入と売上の断絶 |
| Sentryで導線を計測する | Sentryはエラー監視であり、ファネル分析ツールではない |

## 4. 評価指標の設計

### 4.1 単一CVRを廃し、3ファネルに分割する

| ファネル | 対象 | 主指標 | 実測量 |
|---|---|---|---|
| **A. EC（お米）** | `/rice`, 米商品ページ | 購入数・ROAS | 約14件/月・通年安定 |
| **B. EC（いちご）** | `/strawberries`, いちご商品 | 購入数・ROAS | 約10件/月・冬春のみ |
| **C. いちご狩り（送客）** | `/strawberry-picking` | 問い合わせ・電話クリック | 約15件/月・冬春のみ |

分割の根拠:

1. Cの成果はECの数値に一切現れない。混合している限り、いちご狩り施策の効果は永久に不可視。
2. AとBは季節が逆であり、通年の「サイト全体CVR」は両者の混合比の変化にすぎない。
3. 現行の広告キャンペーン構成（いちご通販／無農薬米／いちご狩り）と1対1で対応し、
   指標と打ち手が直結する。

### 4.2 横断指標としてLTV

購入ユーザー105人・平均1.28回という実測値が既にある。LTVは**季節性の影響を受けない
唯一の指標**であり、主要な改善対象とする。GA4では取得不能なため
Shopify Admin API を第2のデータソースとする。

### 4.3 使用しない指標

- `bounceRate` — GA4拡張計測により全行0を返す。このプロパティでは無意味。
- サイト全体CVR — 4.1の理由により使用しない。

## 6. サブプロジェクト1：計測基盤（最優先・期限 2026-11月末）

### 6.1 期限の根拠

いちごシーズンは12月に始まる。11月末までに計測を修正すれば、
**クリーンなデータでピークシーズンを丸ごと記録できる最初の機会**となる。
逃した場合、次の機会は2027年12月。

### 6.2 イベント所有権ポリシー（最重要の設計判断）

Shopifyの Google & YouTube チャネル連携がチェックアウトドメイン上で独自にGA4イベントを
送信している。自社サイトと同じイベントを撃つと二重計上になる。**カートを境界線とする。**

| イベント | 所有者 | 現状 | 対応 |
|---|---|---|---|
| `page_view` | 自社サイト | 拡張計測が代行（パス不整合） | 自前送信に置換 |
| `view_item_list` | 自社サイト | なし | 追加 |
| `view_item` | 自社サイト | なし | 追加 |
| `add_to_cart` | 自社サイト | あり（buyNow経路欠落） | buyNowにも追加 |
| `view_cart` / `remove_from_cart` | 自社サイト | なし | 追加 |
| `begin_checkout` | **Shopify** | Shopify送信済（339件） | **自社では実装しない** |
| `add_shipping_info` / `add_payment_info` | **Shopify** | 送信済 | 触らない |
| `purchase` | **Shopify** | 送信済（134件） | **未使用関数を削除** |
| `contact_form_submit` | 自社サイト | あり（種別なし） | 種別パラメータ追加 |
| `phone_click` 等 | 自社サイト | `click` に集約され分解不能 | 独立イベント化 |

**帰結（重要）:**

- `CartDrawer` に `begin_checkout` を追加してはならない。Shopifyが既に339件送信しており、
  追加すると全チェックアウトが二重計上される。
- `analytics.ts` の `trackBeginCheckout()` / `trackShopifyPurchase()` は
  「未使用だから無害」ではなく「**呼び出してはならない関数**」である。
  将来の実装者が誤って接続する罠となるため削除する。
- `begin_checkout`(339) > `add_to_cart`(304) という逆転の原因は、**`addToCart` の
  呼び出し4箇所のうち3箇所で `trackAddToCart` が呼ばれていない**こと（コード実測）。

  | 呼び出し箇所 | `trackAddToCart` |
  |---|---|
  | `ProductByHandlePage.tsx:86` | あり |
  | `StrawberriesPage.tsx:45` | **なし** |
  | `RicePage.tsx:44` | **なし** |
  | `OrderHistory.tsx:65`（マイページからの再注文） | **なし** |

  漏れているのは一覧ページという主要な購入経路であり（ランディング実測で `/rice` から
  14件、`/strawberries` から6件）、さらに `OrderHistory` の再注文は**リピート購入導線
  そのもの**であるため、LTV分析の中核が計測できていない。

- `CartContext` の `buyNow` は定義・exportされているが**どこからも呼ばれていない
  デッドコード**である。計測欠落の原因ではない。

### 6.3.1 訂正：`click` と問い合わせ種別は「分解不能」ではなかった

初版で「`event_category` / `event_label` は未登録のカスタムパラメータであり、
GA4レポートで分解できない」と記述したが、**誤りだった**。GA4 Admin API で確認したところ、
両者は EVENT スコープのカスタムディメンションとして**既に登録されている**。

実測（直近12ヶ月）:

| イベント | `event_label` | 件数 |
|---|---|---:|
| `click` | `phone_click` | **225（全件）** |
| `contact_form_submit` | いちご狩りについて | 83 |
| `contact_form_submit` | その他 | 23 |
| `contact_form_submit` | いちごの購入について | 9 |
| `contact_form_submit` | お問い合わせ | 9 |
| `contact_form_submit` | アクセス・営業時間について | 5 |

`click` は全件が電話クリックである（`trackExternalLinkClick` / `trackEmailClick` は
コード上どこからも呼ばれていないため、送信実績が0）。
**したがって、いちご狩りの電話予約導線は現時点でも測定できている。**

修正項目7・4を実施する理由は「不能を可能にする」ことではなく、以下の3点に改める。

1. **登録への依存を外す。** 現状はカスタムディメンションの登録が生きていることに
   依存している。登録が消えれば過去データごと分解不能になる。イベント名で意味が
   決まる形（`phone_click`）なら、その依存がない。
2. **`event_label` は自由文字列であり分類として脆い。** 実測でも `その他` 23件・
   `お問い合わせ` 9件と、意味を持たないラベルが25%を占める。Gmail 側の実測では
   この「その他」の中に玄米購入やいちご狩り予約が混在していた（§2.4）。
   `inquiry_type`（項目4）は本文も含めて分類するため、この取りこぼしを解消する。
3. `trackEmailClick` がメールアドレス全体を送信していた問題を、あわせて解消する。

### 6.3.2 拡張計測の状態確認で踏んだ罠（記録）

GA4 Admin API の `enhancedMeasurementSettings` は、`streamEnabled` と
`searchQueryParameter` のみを返し、個別トグル（ページ変更・スクロール・外部リンク等）を
**1つも含まなかった**。Protobuf JSON は false のフィールドを省略するため、
「全て OFF」と読める。

**しかしこれは誤読である。** 実データが否定した:

- ルーター内部遷移が積むスラッシュなしパス `/strawberries` が 1,095 PV 存在する
- pv/session が 1.38〜1.78（トグルが OFF で初回表示しか記録されないなら 1.0 付近になる）

つまり「ブラウザの履歴イベントに基づくページの変更」は **ON である**。
§6.3 項目2（`page_view` の自前送信）の後に**この設定を無効化しなければ、
全ページビューが二重計上される**。

**教訓: APIの応答にフィールドが存在しないことは、その値が false であることを意味しない。**
設定状態は API の省略ではなく、実データの挙動で確認する。

### 6.4 確認済み：クロスドメイン計測は正常動作している

`無農薬米` キャンペーンに購入16件・¥178,050が紐付いている。セッションが分断されていれば
全購入が `(direct)` に落ちるため、`client_id` がドメインを跨いで継続していることの証拠。
**クロスドメイン対応の工事は不要。**

## 7. サブプロジェクト2：データ集約

### 7.1 方式：リポジトリ内JSONスナップショット

年間データ量が数百KBに収まる規模であり、BigQueryは運用コストに見合わない。

```
data/snapshots/YYYY-MM-DD/
  ga4.json        # ファネル別セッション・購入・売上
  gsc.json        # クエリ別・ページ別
  ads.json        # キャンペーン別
  shopify.json    # 注文・顧客・LTV
  inquiries.json  # 問い合わせ種別
```

git履歴がそのまま時系列となり、`git log -p data/snapshots/` で
**指標の変化と施策のコミットが同一の履歴上に並ぶ**。

### 7.2 BigQueryエクスポートは有効化のみ実施

エクスポートは連携日以降しか蓄積されない。使わなくても損失はないが、
連携しなかった期間は回復不能。オプション価値として早期に有効化する。

### 7.2.1 必須のフィルタ：開発トラフィックの除外

ローカル開発（`npm run dev`）や外形評価（§10.4）で発生したイベントは、本番と同じ
GA4プロパティに記録される。実測（2026-09-05）では以下のように分離できている。

| hostName | 内容 | 当日のイベント数 |
|---|---|---|
| `www.tsuru-strawberry-farm.com` | 本番サイト | 23 |
| `shop.tsuru-strawberry-farm.com` | Shopifyチェックアウト | 12 |
| `localhost` | 開発・検証 | 4 |

**すべての集計クエリで `hostName` が `localhost` の行を除外する。**

コード側で localhost の送信を抑止する案は採用しない。§10.4 の外形評価は
「イベントが実際に発火するか」を実ブラウザで確認する仕組みであり、送信を止めると
**検証手段そのものが機能しなくなる**ため。送信は許し、集計時に除外する。

### 7.2.2 既知の罠：EC系イベントのページ次元は正規化されていない

`page_view` のみ、アプリ側で `page_location` を正規化済みパスで上書きしている。
一方 `view_item` / `view_item_list` / `add_to_cart` / `view_cart` / `remove_from_cart` /
`phone_click` は gtag が内部で付与する生の `document.location` を運ぶ。

つまり **§6.3 項目2で解消した末尾スラッシュの分裂は、EC系イベントのページ次元には
残っている**。GitHub Pages の直接アクセスでは `/rice/`、SPA遷移後は `/rice` になる。

**集計スクリプト側の必須対応:** EC系イベントを `pagePath` で集計する場合は、
スクリプト内で末尾スラッシュを除去してから集約すること。
あるいは EC系イベントをページ次元で切らず、`item_category` で切る。
後者のほうが設計意図（§4.1 のファネル分割）に合致する。

### 7.3 既知の罠：`advertiserAdCost` × 日付ディメンション

**GA4 Data API で `advertiserAdCost` を `yearMonth` でグルーピングすると、
日数分（2月なら28倍）に水増しされる。エラーも警告も出ない。**

実測（2026年2月）:

| 集計方法 | 結果 |
|---|---:|
| `sessionCampaignName` のみ | ¥71,853（正） |
| `yearMonth` × `sessionCampaignName` | ¥1,836,979（**28倍**） |
| `date` × `sessionCampaignName`（5日分から換算） | 約¥59,000（整合） |

**対策:** 広告費の集計には `date` または `sessionCampaignName` のみを使用し、
`yearMonth` と組み合わせない。集計スクリプトにこの制約をコメントで明記し、
日次値の合計と月次値を突き合わせる検証を自動テストとして組み込む。

## 8. サブプロジェクト3：仮説台帳（GitHub Projects v2）

`gh` CLI が `project` スコープを保有済みのため、追加の認証基盤は不要。
仮説チケットと実装PRが同一プラットフォーム上で自動リンクする。

### 8.1 カスタムフィールド

| フィールド | 型 | 目的 |
|---|---|---|
| 仮説 | テキスト | 「〜なので、〜すれば、〜が改善する」形式 |
| 対象ファネル | 選択 | EC-いちご / EC-お米 / いちご狩り / 横断 |
| 施策種別 | 選択 | SEO / コピー / 画像 / UI / 広告 / 計測 |
| 検証階層 | 選択 | T1機能 / T2先行指標 / T3結果指標 / T4前年比 |
| 評価指標 | テキスト | 何をどこで見るか |
| 観測終了日 | 日付 | **起票時に確定させる** |
| ステータス | 選択 | 仮説 → 実装中 → 観測中 → 判定済み |
| 結果 | 選択 | 採用 / 棄却 / **判定不能** |

### 8.2 設計上の要点

1. **「判定不能」を正式な結果として持つ。** 月11件の購入では、T3の施策の大半は
   統計的に判定できない。それを「たぶん効いた」と記録すると、ループはノイズを学習し、
   確信を持って改悪を続ける。判定不能を正直に記録できるかがループの成否を分ける。
2. **観測終了日を起票時に確定する。** 後から決めると、良く見えたタイミングで
   結果を確定させてしまう（実行者本人は気づけない）。

## 9. サブプロジェクト4：AIループと自動化の境界

### 9.1 自動化レベル

金銭的取引のある顧客案件ではないため、自動化は積極的に設定する。
守るべきは「不可逆な損失」のみとする。

| フェーズ | 実行者 | ガードレール |
|---|---|---|
| データ収集 → スナップショットcommit | 完全自動（Python） | なし。トークン消費なし |
| 週次レポートissue起票 | 完全自動 | なし |
| 観測終了チケットの判定 | AI | 「判定不能」を選択可能にする |
| 新仮説の起票 | AI | 週3件まで |
| PR作成 | AI | — |
| **PRマージ → デプロイ** | **AI（自動）** | **クリーンな `npm ci` からのビルド成功**＋スモークテスト通過が必須（9.1.1参照）。**カート・チェックアウト・購入経路に触る変更は人間レビュー**。デプロイ後に主要ページのHTTP 200とGA4イベント発火を検証し、失敗時は自動revert |
| **広告予算の変更** | **AI（自動）** | 週次変更幅±20%以内／月間上限額を固定／必ず台帳チケットに紐付け／連続2週の悪化で自動ロールバック |
| 価格変更・商品追加 | 人間 | 在庫・実物が絡むため |

### 9.1.1 自動マージのゲート条件（実地の失敗から改訂）

本計画の実装中に、**テストも型検査も通るのに本番デプロイが壊れる**変更が実際に発生した。
自動マージのゲート条件はこの事例を踏まえて定義する。

**何が起きたか:** 依存追加のための `npm install` が `package-lock.json` を再生成した際、
`peerDependenciesMeta` で `optional: true` と宣言されていた `react` / `react-dom` が
lockfile から削除された。CI は `npm ci`（lockfile厳密インストール）で動くため、
React がインストールされず `vite build` が失敗する状態になっていた。

**なぜ既存のゲートで捕まらなかったか:**

| 検査 | 結果 | なぜ見逃したか |
|---|---|---|
| `npm test` | 通過 | ローカルの `node_modules` に React が残っていた |
| `npm run typecheck` | 通過 | 同上 |
| 実装者の自己レビュー | 通過 | 差分の大半が lockfile の機械的変動 |
| コードレビュー（AI） | Spec ✅ / Approved | lockfile を「ノイズ」として読み飛ばす指示を出していた |

**改訂後のゲート条件:**

1. **クリーンな `npm ci` からビルドが通ること。** ローカルの `node_modules` は
   lockfile の欠落を隠す。既存の `node_modules` を再利用した検証は無効とする。
2. **依存の削除を差分レビューの明示的な確認項目とする。** lockfile への依存の
   出入りは挙動の変更であり、レビュー指示で読み飛ばしを指示してはならない。
3. デプロイ後の実ページ検証（§9.1）は維持する。

### 9.2 停止スイッチ

リポジトリ内のフラグファイル1つで全自動処理を停止できるようにする。
異常時に人間が確実に止められることを、自動化の前提条件とする。

### 9.3 広告操作の実装経路

Google Ads API は developer token の申請承認が必要で、リードタイムが読めない。
**Google Ads スクリプト**（Ads管理画面内で動作、予算変更・スケジュール実行が可能、
developer token 不要）を第一候補とする。API は将来の選択肢として残す。

### 9.4 コスト設計

データ収集・レポート生成を純粋なPythonで完全自動化し、AIを使わない部分を最大化する。
これによりトークン費用を抑えつつ「データは毎週必ず蓄積される」状態を保証する。
**AIが停止してもデータ収集は止まらない。**

## 10. サブプロジェクト5：検証方法論

### 10.1 検証階層

検証は**定量（T階層）と定性（Q階層）の2軸**で構成する。
Q階層が仮説を生み、T階層が（可能な場合のみ）検証する。

| 階層 | 対象 | 頻度 | 検証通貨 |
|---|---|---|---|
| **Q** | ユーザー体験・購入の躊躇 | 常時 | **セッションリプレイ・ヒートマップ・外形評価**（10.3 / 10.4） |
| **T1** | 計測欠陥の修正 | 都度 | **Claude in Chrome による実イベント発火確認**（10.4）。CVRでは検証しない |
| **T2** | SEO・コピー・画像 | 週次 | Search Console（表示回数・CTR・掲載順位） |
| **T3** | 売上・広告 | 月次 | 購入数・ROAS。**大きな効果しか検出できないことを明記して運用** |
| **T4** | 通年比較 | 2026-12以降 | 前年同期比 |

A/Bテストは実施しない（3章参照）。

**Q階層が主たる証拠源である。** 年間購入者は105人であり、統計的検証には不足だが、
**全購入セッションを個別に観察することが可能な規模**である。
大規模サイトでは不可能な密度の定性観測が成立する。

### 10.2 T2をSearch Consoleで行う理由

購入134件/年・カート追加304件/年では、SEO施策の効果は統計的に永久に検出できない。
一方GSCはクエリ別・ページ別の表示回数が週次で数百規模動くため、
**週次で検証可能な唯一の定量データソース**である。

### 10.3 定性観測レイヤー：PostHog

GA4は「何人が離脱したか」は答えるが、「**なぜ躊躇したか**」には答えない。
本サイトの規模では後者こそが行動可能な情報である。

**導入するもの:**

| 機能 | 用途 |
|---|---|
| セッションリプレイ | 購入直前の離脱・カート放棄の実際の挙動を観察する |
| ヒートマップ / スクロール深度 | 価格・送料・購入ボタンが実際に見られているかを確認する |
| オートキャプチャ | 事前定義なしに全クリックを記録する |
| ファネル（遡及定義） | 過去データに対して後からファネルを定義し直せる |

**GA4に対する優位点:**

- GA4はカスタムパラメータの**事前登録**が必要であり、登録し忘れた軸は永久に分解できない
  （§6.3 項目7 の `click` イベント問題がまさにこれ）。PostHogのオートキャプチャは
  この種の取りこぼしを構造的に発生させない。
- セッションリプレイにより、`/strawberries` が `/rice` よりCTR・CVRともに大幅に劣る理由を
  **推測ではなく観察で**特定できる。

**コスト:** PostHog Cloud の無料枠（月100万イベント／セッションリプレイ数千件規模）で
収まる見込み。本サイトのピーク月は3,581セッションであり、無料枠に対して十分小さい。
**ただし無料枠の具体的数値は導入時に実測で確認すること**（料金体系は変動する）。
セルフホストは可能だがホスティング費が無料枠を上回るため採用しない。

**必須の前提条件（個人情報）:**

セッションリプレイは**実在の顧客の操作を録画する**。以下を導入の必要条件とする。

1. 入力フォームのマスキングを有効化する（氏名・メール・電話・住所を記録しない）
2. `/privacy-policy` に録画の事実・目的・オプトアウト手段を明記する
3. Shopifyチェックアウトドメインには**導入しない**（決済情報に近接するため）

### 10.4 外形評価レイヤー：Claude in Chrome

実ブラウザで実サイトを操作し、外側から評価する。以下の4用途で使用する。

| 用途 | 内容 | 頻度 |
|---|---|---|
| **T1検証** | 計測修正後に実際に画面を操作し、コンソール・ネットワークから**イベントが実際に発火しているか**を確認する。§10.1 T1の「機能確認」の実装 | 修正の都度 |
| **デプロイ後スモークテスト** | §9.1 の自動マージ後の検証。主要ページの表示・カート投入・チェックアウト遷移を実操作で確認し、失敗時は自動revertを起動する | デプロイ毎 |
| **外形UX評価** | **モバイル表示**（セッションの81%・購入の85%）で購入導線を実際に辿り、摩擦を報告する | 週次 |
| **競合比較** | GSCで検出された競合（`berry's farm sakura`, `soil select farm` 等）のサイトを外形評価し、差分を仮説として起票する | 月次 |

**この層が必要な理由:** T2〜T4はいずれも「起きた結果」しか観測できない。
Q階層とこの外形評価だけが、**施策を打つ前に問題を発見できる**。
